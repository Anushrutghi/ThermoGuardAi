# ThermoGuard AI — Data Contracts & Schema Specification

**Document Version:** 1.0.0  
**Status:** Canonical Reference  
**Last Updated:** September 2026  

---

## 1. Executive Summary & Principles

ThermoGuard AI requires strict data fidelity to serve as a trustworthy electrical inspection assistant. Every physical measurement, visual finding, and diagnostic hypothesis must carry unambiguous semantics, provenance, and units.

### Core Architectural Invariants:
1. **Never Encode Missing Temperature as Zero:** $0.0^\circ\text{C}$ is a valid physical temperature that occurs in cold storage, outdoor switchgear during winter, or unenergized circuits. Missing temperature MUST be explicitly `None` (`null` in JSON) paired with an explicit `TemperatureStatus` explaining why the reading is absent.
2. **Strict Separation of Measured vs. Simulated Data:** Readings produced by simulation engines (`ThermalSimulator`) must carry `provenance=SYNTHETIC` and `status=SIMULATED`. Real-world analytics (Remaining Useful Life, failure probability, peer delta) must exclude simulated records by default.
3. **Separation of Visible Evidence from Fault Hypotheses:** A visible burn mark, discoloration, or loose wire is a physical optical finding (`VisibleEvidenceItem`). An "overloaded circuit" or "loose connection" is an inferred diagnostic hypothesis (`FaultHypothesis`) with confidence and evidence lineage. They are never conflated.
4. **Explicit Units and UTC Timestamps:** All physical units are explicitly documented and reflected in field names (`_c` for Celsius, `_ms` for milliseconds, `_s` for seconds, `_m` for meters). All timestamps are ISO 8601 UTC strings (`YYYY-MM-DDTHH:MM:SS.mmmmmmZ` or `+00:00`).
5. **Backward Compatibility:** All existing endpoints (`DetectionOut`, `FaultOut`, `IncidentOut`) continue to serialize existing fields without breaking changes while exposing additive contract fields.

## 2. Canonical Enums

### 2.1 `ObservationProvenance`
Specifies the ultimate origin of an observation or measurement:
- `MEASURED`: Hardware sensor (e.g. calibrated FLIR radiometric sensor, MLX90640 I2C array).
- `SYNTHETIC`: Generated by a software simulation engine (e.g. demo mode or test fixture).
- `DERIVED`: Computed mathematically from multiple readings (e.g. ambient rise $\Delta T$, peer comparison).
- `MANUAL`: Entered or verified by a qualified human inspector.

### 2.2 `ThermalDataQuality`
Evaluates the reliability of thermal radiometric data:
- `VALID`: Sensor calibrated, stabilized, high Signal-to-Noise Ratio (SNR).
- `UNSTABLE`: Sensor undergoing thermal stabilization (shutter recalibration / NUC) or temperature drift.
- `DEGRADED`: Low SNR, extreme ambient conditions, optical reflection, or low thermal contrast.
- `INVALID`: Packet loss, I2C/SPI bus error, frame corruption, or missing calibration coefficients.
- `SIMULATED`: Synthetic frame from test harness.
- `UNKNOWN`: Uncalibrated or unverified source.

### 2.3 `TemperatureStatus`
Unambiguously defines the validity or specific reason for missing temperature:
- `MEASURED`: Legitimate numeric measurement from hardware sensor.
- `SIMULATED`: Numeric value produced by simulation engine.
- `MISSING_NO_SENSOR`: No thermal camera or infrared sensor attached to the inspection pipeline.
- `MISSING_INVALID_FRAME`: Thermal frame dropped, unreadable, or failed radiometric calibration.
- `MISSING_OCCLUDED`: Target component occluded by barrier, conduit, or wiring bundle.
- `MISSING_OUT_OF_RANGE`: Target temperature exceeds sensor calibration boundaries.

### 2.4 `CoverageStatus`
Indicates inspection completeness for a target component:
- `FULL`: Component completely visible in visual frame and within thermal FOV.
- `PARTIAL`: Component partially cropped at frame boundary or partially masked.
- `OCCLUDED`: Major portion obscured by physical obstacles or dead zone.
- `INSUFFICIENT_EVIDENCE`: Lighting, distance, or focus prevents reliable assessment.

### 2.5 `SeverityLevel`
Standardized risk classification:
- `NORMAL`: Nominal operation, within design tolerances.
- `MONITORING`: Minor thermal or visual variance; trend monitoring recommended.
- `WARNING`: Clear anomaly; scheduled maintenance intervention required.
- `CRITICAL`: Dangerous thermal rise or severe physical damage; immediate action required.

### 2.6 `IncidentStatus`
Lifecycle state of an evidence-backed incident:
- `OPEN`: Initial detection created by inspection pipeline.
- `INVESTIGATING`: Assigned to technician or maintenance team for root-cause analysis.
- `ACTIONED`: Work order issued or physical repair in progress.
- `RESOLVED`: Maintenance verified, temperatures returned to nominal.
- `FALSE_POSITIVE`: Reviewed and rejected by qualified inspector.
- `CLOSED`: Administratively closed and archived.

### 2.7 `ComponentConditionState`
Persistent health state of a physical asset:
- `HEALTHY`: No active warnings or anomalies.
- `SUSPECT`: Minor anomaly or low-confidence hypothesis detected.
- `DEGRADED`: Confirmed fault or repeated elevated temperature.
- `FAILED`: Inoperative, tripped breaker, or burnt contact.
- `UNKNOWN`: Uninspected or stale data.

## 3. Data Contracts Specification

### 3.1 `TemperatureReadingContract`
Encapsulates temperature data with rigorous semantic validation.

| Field | Type | Required | Units / Constraints | Description |
|---|---|---|---|---|
| `status` | `TemperatureStatus` | Yes | Enum | Reading status or missing reason. |
| `temperature_c` | `float \| None` | Conditional | Degrees Celsius ($^\circ\text{C}$) | Measured temperature. **Must be `None`** if status is `MISSING_*`. **Cannot be `None`** if status is `MEASURED` or `SIMULATED`. |
| `ambient_c` | `float \| None` | No | Degrees Celsius ($^\circ\text{C}$) | Surrounding ambient temperature baseline. |
| `delta_t_c` | `float \| None` | No | Degrees Celsius ($^\circ\text{C}$) | Temperature rise above ambient or peer differential. |
| `emissivity` | `float \| None` | No | $0.01 \le \epsilon \le 1.00$ | Surface emissivity used for Planck radiometry. |
| `provenance` | `ObservationProvenance` | No | Default `MEASURED` | Source of data. |
| `sensor_id` | `str \| None` | No | String | Unique hardware sensor identifier. |
| `measurement_confidence` | `float` | No | $0.0 \le c \le 1.0$ | Confidence in thermal calibration. |

#### Validation Invariants:
- If `status in {MISSING_NO_SENSOR, MISSING_INVALID_FRAME, MISSING_OCCLUDED, MISSING_OUT_OF_RANGE}`, then `temperature_c` must be `None`. Supplying any numeric float (including `0.0`) raises a validation error.
- If `status in {MEASURED, SIMULATED}`, then `temperature_c` must be a valid float (e.g. `0.0` is accepted as physical freezing point).
- If `provenance == SYNTHETIC`, status cannot be `MEASURED`.

### 3.2 `VisibleEvidenceItem`
Verifiable optical evidence observed in RGB or grayscale inspection frames.

| Field | Type | Required | Constraints | Description |
|---|---|---|---|---|
| `anomaly_type` | `str` | Yes | String | Anomaly category (e.g. `discoloration`, `burn_mark`, `loose_wire`). |
| `confidence` | `float` | No | $0.0 \le c \le 1.0$ | Visual detection confidence. |
| `bbox` | `list[float] \| None` | No | $[x_1, y_1, x_2, y_2] \in [0, 1]$ | Normalized bounding box of visible anomaly. |
| `description` | `str \| None` | No | String | Narrative description of physical evidence. |
| `evidence_image_path` | `str \| None` | No | URI / File path | Cropped evidence image path. |

## 4. Database Schema & Migration Strategy

### 4.1 Additive Migrations (`backend/db/session.py`)
To preserve backward compatibility and ensure zero downtime:
- **Never drop or rename existing columns.**
- New columns are defined in `_COLUMN_ADDITIONS` with safe nullable or default values.
- New indexes are registered in `_INDEX_ADDITIONS`.
- In SQLite development/tests, `_ensure_columns()` uses `PRAGMA table_info` and issues `ALTER TABLE {table} ADD COLUMN {col} {ddl}`.
- In PostgreSQL/production, `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` is executed.

#### Columns Added in This Upgrade:
```python
_COLUMN_ADDITIONS = {
    # incidents table
    "incidents": [
        ("status", "VARCHAR(32) DEFAULT 'OPEN'"),
        ("device_id", "INTEGER"),
        ("panel_id", "INTEGER"),
        ("component_id", "INTEGER"),
        ("delta_t", "FLOAT"),
        ("peer_comparison", "TEXT"),
        ("evidence_thermal_path", "VARCHAR(512)"),
        ("resolved_at", "DATETIME"),
        ("resolved_by", "VARCHAR(64)"),
        ("resolution_notes", "TEXT"),
    ],
    # temperature_history table
    "temperature_history": [
        ("simulated", "BOOLEAN DEFAULT 0"),
    ],
}
```

### 4.2 Cloud Firestore Document Model
In Cloud Firestore (`STORAGE_BACKEND=firestore`), documents under the `incidents` collection adopt the same contract structure:
```json
{
  "code": "INC-20260923-1-01",
  "status": "OPEN",
  "inspection_id": 1,
  "device_id": 4,
  "panel_id": 2,
  "component_id": 15,
  "component_label": "circuit_breaker",
  "component_code": "B1",
  "fault_type": "overloaded_circuit",
  "severity": "CRITICAL",
  "temperature": {
    "status": "MEASURED",
    "temperature_c": 78.4,
    "ambient_c": 22.1,
    "delta_t_c": 56.3,
    "provenance": "MEASURED",
    "sensor_id": "mlx90640-i2c-1",
    "measurement_confidence": 0.95
  },
  "occurred_at": "2026-09-23T11:20:00.000000Z",
  "evidence_thermal_path": "storage/evidence/thermal_101.png"
}
```
Existing Firestore documents without these fields default gracefully when loaded via Pydantic (`status="OPEN"`, nullable fields as `None`).
